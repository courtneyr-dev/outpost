## Session F14 — Locked Decisions (shipped)

Closed 2026-05-04. Promotes the Bridgy host-pattern logic to a full `Outpost_Bridgy_Publish_Adapter` covering the five May-2026-confirmed Bridgy Publish silos: Mastodon, Bluesky, Flickr, GitHub, Reddit. Same umbrella pattern as F9 ManualShare. F14 ships chip surfaces + settings + response handling; webmention SENDING is deferred (no existing sender exists in Outpost).

1. **One companion, five silos via declarative configs.** `Outpost_Bridgy_Publish_Adapter` extends `Companion_Base` with `platform_chips()` returning per-silo chips. Same umbrella pattern as F9 — config arrays drive everything, no per-silo PHP class.
2. **Settings opt-in is authoritative; default state is all off.** `Outpost_Bridgy_Publish_Settings` stores per-silo bool toggles in `outpost_bridgy_silos_enabled` option. `is_enabled($silo_chip_id)` returns false until user explicitly toggles. The webmention-history hint mentioned in the prompt is deferred — opt-in via settings is the single signal.
3. **Bridgy URL must point at brid.gy.** `Silo_Config::normalize_and_validate` rejects `bridgy_url` values that don't start with `https://brid.gy/publish/` or `https://fed.brid.gy/`. Defense against filter-registered configs accidentally pointing at evil hosts.
4. **`outpost_bridgy_publish_silos` filter is the documented extension point.** Filter callers can append (future Bridgy silos), remove (defaults), or modify (caveats per site policy). Same pattern as F9's `outpost_manual_share_platforms`.
5. **Bridgy_Silo_Detector is fuzzy on Mastodon, exact on others.** Mastodon detection: `.social` / `.cloud` / `.online` / `.network` TLD suffix patterns plus `outpost_bridgy_mastodon_hosts` filter for explicit allowlisting. Bluesky / Flickr / GitHub / Reddit: exact host or known suffixes (no fuzzy match). The detector is a hint utility for composer-side "user pasted a URL — which Bridgy chip?" — false positives are tolerated since user explicitly opts into chips via settings.
6. **F9's reddit-manual + flickr-manual chips defer per-platform when matching Bridgy silo enabled.** `Outpost_Manual_Share_Adapter::bridgy_chip_enabled_for_platform()` maps `reddit-manual` → `reddit` silo id, `flickr-manual` → `flickr`. When the Bridgy silo is enabled in settings, the manual chip drops. User sees one chip per destination, not two.
7. **Webmention SENDING deferred — no existing sender in Outpost.** F12 #11 already documented this. F14 ships the response-PROCESSING path (`Webmention_Response_Handler::process_response`) so when a sender lands the wiring is one connector away. F14 tests cover response parsing in isolation against synthetic Bridgy response bodies.
8. **Webmention success writes silo URL to F12's `outpost_syndication_links`.** Bridgy returns the published silo URL in its 2xx response (as JSON `url` field, JSON `silo_url` field, or plain-text body). The handler extracts via fallback chain, then calls `Outpost_Manual_Share_Syndication_Writeback::add_or_update_link()` so the post's `u-syndication` rendering picks up the Bridgy-published URL automatically.
9. **Webmention failures recorded in `outpost_bridgy_publish_log` with error_code + error_message.** Separate post-meta from F12's `outpost_syndication_links` because the audit shape differs (Bridgy entries care about Bridgy-specific error codes; F12 entries only care about silo URLs that succeeded). F13's status surfacing pattern can be extended to surface Bridgy publish failures in a future session.
10. **`get_option` mock added to existing test setUps that touch the registry.** `CompanionRegistryTest`, `CompanionLoaderEdgeCasesTest`, `ManualShareAdapterTest` now mock `get_option` because the new Bridgy adapter is instantiated whenever the registry is iterated, and the adapter reads settings via `get_option`. The default mock returns empty array (no Bridgy configured) preserving F1–F13 test semantics. Captured here so future companion adapters that read settings from the start ship with the test mock pattern.
11. **No webmention sender, so no PWA composer integration in F14.** F14 ships server-side classes + admin settings page contract + PWA setup modal as a separate component. Composer-side mounting (where Bridgy chips render in the user-facing composer view) deferred consistent with F10/F11/F12/F13's "ship modules in isolation; integrate when all the pieces exist" stance.
12. **Naming divergences from prompt.** Prompt: `Companion_BridgyPublish.php`, `Silo_Registry.php`, `Bridgy_Settings.php`, `Webmention_Response_Handler.php`, `Publish_Log.php`, `Bridgy_Settings_Page.php`. Tests in `tests/unit/`. Continues F9–F13 pattern.
